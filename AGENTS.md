# Agent instructions

## The project

Ocean Mist is a music player for Linux with the look of Windows Media Player 9: the sculpted frame, the visualizations, a 10-band equalizer, a media library, internet radio, playlists, YouTube Music and your Apple Music library, which plays through a playback engine the user downloads on request. The interface is a local web page (`ui/`) shown in a frameless WebKitGTK window; `player.py` owns the window and a small HTTP server bound to 127.0.0.1 that feeds the page. There is no build step and nothing to install beyond GTK 3, WebKitGTK 4.1 and GStreamer; the Python side uses the standard library only. `README.md` describes the features.

It is an unofficial fan project, not affiliated with Microsoft, and licensed under GPL-3.0-or-later (`LICENSE`).

Never describe something as working or complete unless a recorded check establishes it. A syntax check is not proof that the player behaves.

## Layout

| :--- | :--- |

| `library.py` | The two Now Playing lists (My Music, saved in `state.json`; YouTube Music, in memory only, where Apple Music songs sit as tracks with an Apple address, and their library id when it differs), media library scan, saved playlists, radio stations, settings, resume point (a file or a station) |
| `tags.py` | Titles, covers and lengths from MP3, FLAC, Ogg Vorbis, Opus, M4A and WAV, standard library only |
| `radio.py` | Relays an internet radio stream to the page and reads its song titles |
| `ytmusic.py` | YouTube Music without an account: search, albums, artists, playlists, similar songs, covers, and each song's audio (HLS segments repacked as MP4 fragments); signed in, the library, likes and playlist changes. Standard library only |
| `apple.py` | Apple Music through Apple's own web page: a windowless, in-memory view of music.apple.com signed in with the Firefox cookie, asked for the library (read-only) through the page's own MusicKit, with every sign-out request blocked. It only reads: the songs are played by the engine. Python standard library only, besides the GTK and WebKit the player already needs |
| `engine.py` | The playback engine for Apple Music songs: after the user's consent on a licence screen it downloads castlabs's build of Electron (Chromium with Widevine support), checks its size and SHA-256 and unpacks it into `~/.local/share/ocean-mist/engine`; starts `engine/helper` only while an Apple song plays, handing it the sign-in on stdin, and ends it a minute after the music stops; checks that Chromium's sandbox starts, and knows when the Debian package's profile names the engine's file (`covered` in the status: the package is installed, which its folder `/usr/lib/ocean-mist` shows, its profile file `/etc/apparmor.d/ocean-mist-engine` exists and no link in `/etc/apparmor.d/disable/` switches it off, and the engine's file sits in the default place of a home folder under `/home`, or root's), so that the page announces no step and a folder name the step could not hold is no reason to refuse; speaks the helper's line protocol and tells the page with `engine` and `engine-setup` events. Python standard library only |
| `engine/helper/` | `main.js`, the Electron main process: a window that is never shown, an in-memory session holding the cookie, Apple's web player (MusicKit) driven from the main process, every sign-out request cancelled, navigation (links, redirects and frames) limited to https addresses of apple.com. `package.json` only names it |
| `engine/allow-sandbox.sh` | The administrator step on Ubuntu 24.04 and later for an engine file the package's profile does not name (no package, or a data folder that is not the default one): an AppArmor profile that lets that one `electron` file create the user namespaces its sandbox uses. The player asks for it through `pkexec`, after the system's own password window (the password goes to the system, never to Ocean Mist, and `PKEXEC_UID` says who asked), and takes it away the same way for as long as the profile is on the system; where there is no `pkexec` or it did not work, the page shows the command and the one that undoes it, for a terminal. The script runs only when started, so a check can load its functions |
| `firefox.py` | The YouTube and Apple Music sign-ins of the user's Firefox: finds the profiles and their names, reads a cookie file and its write-ahead log read-only into memory, and signs a request the way the site does (YouTube) or hands over the one cookie Apple's page needs (Apple Music). Standard library only |
| `mpris.py` | The desktop's media controls and media keys (MPRIS) |
| `ui/frame.js` | The sculpted frame and the compact frame, drawn as SVG |
| `ui/app.js` | Playback core, the two lists and the switch between them (the second is named after the service its songs come from), menus, queue, keyboard, the Media Source feed for YouTube Music songs, and for Apple Music songs the mirror of what the playback engine plays (the `engine-*` commands out, the `engine` events in); exposes `window.Mist` to the other scripts |
| `ui/premium.js` | Premium Services: the YouTube Music view with its Now Playing list and saved playlists, the Library (signing in, your playlists, likes and playlist changes), the Apple Music branch (signing in, Recently added, Playlists, Albums, Artists and Songs, a page at a time, Play on a row of Recently added filling the list with the whole feed, and the Playback engine page: licence screen, install, check, the sandbox step, remove), and similar songs when the list runs out |
| `ui/eq.js`, `ui/library.js`, `ui/radio.js`, `ui/skins.js`, `ui/visuals.js` | Equalizer, Media Library, Radio Tuner, Skin Chooser, visualizations |
| `ui/fonts/` | Tahoma look-alike fonts from the Wine project, under their own license (LGPL 2.1 or later; see its `README.md`) |
| `data/` | Application icon and desktop entry template |

## Commands

- `python3 player.py [FILES OR FOLDERS...]` runs the player.
- `python3 player.py --serve PORT [FILES...]` serves the interface without a window, at `http://127.0.0.1:PORT/dev/`, for work on the page alone.
- `python3 -m py_compile player.py library.py tags.py radio.py mpris.py ytmusic.py firefox.py apple.py engine.py`, `for f in ui/*.js engine/helper/main.js; do node --check "$f"; done` and `bash -n engine/allow-sandbox.sh` are the source checks. There is no test suite yet.
- `packaging/build-deb.sh [FOLDER]` builds `FOLDER/ocean-mist_VERSION_all.deb` (default `dist/`, which git ignores) from the last commit (a rebuild of the same commit gives the same bytes on the same tools); `OCEAN_MIST_VERSION=0.2.0` makes a release build (releases so far: 0.1.0). It needs git and dpkg-deb, installs nothing and needs no root. `dpkg-deb --info FILE` and `dpkg-deb --contents FILE` show what it made.
- `OCEAN_MIST_DEBUG=1` logs the HTTP requests and enables the web inspector.
- `python3 ytmusic.py search|album|artist|playlist|radio|audio ...` prints what the YouTube Music engine gets, without the player (the full list is in its docstring).
- `python3 firefox.py` says which Firefox profiles have a YouTube and an Apple Music sign-in, without printing any cookie.
- `python3 engine.py` says whether the playback engine is installed and whether this system restricts user namespaces (read-only); `python3 engine.py check` starts the installed engine for a moment and checks that its sandbox works.
- `python3 apple.py` opens Apple's page with the Apple Music sign-in of the most recently used Firefox profile that has one, and prints counts of what the library holds: no titles, no account details. It reads the owner's account, read-only.

## Working well here

- Start from the active issue, then read only the code involved.
- The look is the point. The frame is measured against the original player, so compare with a reference before changing its shape, sizes or colors, and say in the PR what was compared.
- Keep it dependency-free: no build step, no Python packages, no JavaScript libraries, unless the issue says otherwise.
- Anything bundled from elsewhere (fonts, images, sounds) needs a license compatible with GPL-3.0-or-later, its notices next to the files and a line in the README credits, as in `ui/fonts/`.
- Never run a check against the owner's own player or settings. Use a separate instance and scratch folders, and keep it muted:

  ```sh
  T=/tmp/ocean-mist-test/Issue123
  OCEAN_MIST_APP_ID=io.github.nahuelgenchi.OceanMistTest.Issue123 \
  XDG_CONFIG_HOME=$T/config XDG_CACHE_HOME=$T/cache XDG_DATA_HOME=$T/data python3 player.py
  ```

  Settings live in `$XDG_CONFIG_HOME/ocean-mist/state.json`. Write it before the first launch, as `{"settings": {"muted": true, "folders": ["/tmp/ocean-mist-test/Issue123/music"]}}`: muted, and with the check's generated sample music as the media library, which otherwise scans `~/Music`.
- Other checks may be running at the same time, so each instance gets an app id and scratch folders of its own, named after its check (`Issue123` above, `Issue123B` for a second instance). The app id is the instance's name on the session bus. Its media controls (MPRIS) answer at the app id with `org.mpris.MediaPlayer2` in place of `io.github.nahuelgenchi`, here `org.mpris.MediaPlayer2.OceanMistTest.Issue123`; send the check's media-control calls there and nowhere else. A launch under an app id that is already on the bus goes to the instance holding it: the files open there, replacing its My Music, and the new process exits at once, without a word. So before a windowed launch, list the Ocean Mist names on the bus and make sure neither of the instance's names is there:

  ```sh
  gdbus call --session --dest org.freedesktop.DBus --object-path /org/freedesktop/DBus \
    --method org.freedesktop.DBus.ListNames | grep -o "'[^']*OceanMist[^']*'"
  ```
- WebKitGTK behavior worth knowing: script run from the host counts as a user gesture, so it hides autoplay problems; a seek on a song that has never played is ignored; a cross-origin stream is silent through Web Audio, which is why radio goes through the local relay; media only loads in a real, visible window. It cannot play HLS, which is why YouTube Music songs reach the page as MP4 fragments through Media Source; there, a seek made before the song first plays does work. An ephemeral view (`is_ephemeral`) still sets up the default context's cache and data folders on disk; only an ephemeral `WebContext`, which the player uses, keeps everything in memory.
- A check that signs in uses the owner's own Firefox sign-in, so it stays read-only and reports counts, never titles. Likes and playlist changes are checked against a local stand-in for YouTube Music; they are tried on the owner's account only with the owner's go-ahead.
- Apple Music's library is checked against a stand-in page on `music.apple.localhost` (a MusicKit-like object over invented songs) for everything that has a shape: paging, sign-in states, errors, the block on sign-out requests. The owner's own sign-in is used for one read-only run that reports counts and statuses. WebKit gotchas there: Apple's page crashed the web process a few seconds after it loaded in a view with media, Media Source, encrypted media, WebGL, Web Audio, images or hardware acceleration on, so the windowless view switches them all off (it is only a source of data); and WebKit does not send a `SameSite=None` cookie that is not `Secure`, so a stand-in's token must be `Lax`.
- The playback engine is checked in layers, each against a stand-in for the layer below it. The player and `engine.py` run against a stand-in runtime (a script that speaks the helper's protocol, put where the runtime goes and "downloaded" from a local zip, so the 117 MB download is never repeated; the downloader is checked the same way, with the pinned address, size and checksum handed to an injected fetch). The helper (`engine/helper/main.js`) runs in the real castlabs runtime, started by the real `engine.py`, against a stand-in Apple page on a `.localhost` name with an invented sign-in (`--site=` accepts only such a name; anything else stays music.apple.com). A last, muted and read-only run of the whole player on Apple's own site uses the owner's Firefox sign-in and reports statuses and counts, never a title; do it only with the owner's go-ahead, because a song streaming there can stop one playing on the owner's other devices.
- Ubuntu 24.04 and later let a program create the user namespaces Chromium's sandbox needs only if an AppArmor profile names it. A check started from a program that has a profile of its own (a sandboxed terminal or editor, say) inherits that profile, which may allow them, so it can pass where a launch from the menu would not. The menu's way is `systemd-run --user --collect -- <program>`; without the profile it ends with Chromium's "SUID sandbox helper" message, which `engine.py` turns into the page's one-time step. Never switch the sandbox off (`--no-sandbox`) to make a check pass.
- The package's maintainer scripts run as root on other people's machines, so keep them to loading and unloading the one profile (and leaving it unloaded when the administrator switched it off with `aa-disable`) and byte-compiling the player's own files, make a failure of either never fail the install, and keep them out of every home folder. Their checks run the scripts with stand-ins for `apparmor_parser`, `aa-status`, `py3compile` and `py3clean`, and install, upgrade, remove and purge the package with the real `dpkg` into a scratch root (`dpkg --root=DIR --force-not-root --force-script-chrootless`, not as root), then once more with the real `dpkg`, scripts, `py3compile` and `py3clean` in a private user and mount namespace as an unprivileged user (`unshare --user --map-root-user --mount --pid`, with `/usr` and `/etc` as overlays that write to a scratch folder; the folders the package shares with the system are first made in that writable layer, because the real root's own folders are not writable from there). Never install the package on the machine a check runs on, and never load a profile: that is the owner's step, with one script of their own. The profile is checked with `apparmor_parser -Q -T -K`, which parses and loads nothing (the builder skips it, with a note, where the system's AppArmor is older than 4.0). The package also needs AppArmor 4.0 or later when AppArmor is installed (`Breaks: apparmor (<< 4.0~)`), because the profile starts with `abi <abi/4.0>`.
- The administrator step changes the system, so a check never runs it: the host and page checks put a stand-in where `pkexec` goes (`engine.PKEXEC`) and look at what it was asked. The real password window is tried by the owner, in a separate test instance with its own scratch folders.
- Record what a check covered and what it did not, in the PR.

## Private data

Music files, personal playlists, `state.json`, the tag and cover cache, and any account credentials, cookies or tokens stay out of commits, issues and PRs, and out of a check's output. So do YouTube's audio addresses (`googlevideo.com`): they carry the IP address of whoever asked for them, so never print them in a check's output either. No client id, secret or key for a service is ever committed. Screenshots use generated sample music with invented names, never a real library.

Nothing from a streaming service is written to disk: the YouTube Music list (Apple Music songs included), searches, covers and the signed-in libraries stay in memory, the covers for the media controls go to `$XDG_RUNTIME_DIR` and are removed on close, the web contexts (the page's, and the windowless one that reads Apple Music) are ephemeral, and `state.json` holds files and stations only, plus the Firefox profile the user chose to sign in with, for each service. The one other thing in `$XDG_RUNTIME_DIR` is the folder of rules that keep Apple's page from signing the user out; it holds no data from Apple and goes on close. The playback engine's folder (`$XDG_DATA_HOME/ocean-mist/engine`) holds the runtime that was downloaded and the files Chromium and Google's Widevine module keep there, and nothing of Apple's: the page's session lives in memory. A playlist the user saves is the one exception, on purpose: an Apple Music song in it is saved as its Apple address and `Artist - Title`, nothing else. Keep it that way: storing anything else from a service is the owner's decision.

The sign-in stays Firefox's. Ocean Mist reads Firefox's cookie files only while the user is signed in or signing in: signed in, only that of the profile the user chose; signing in, those of every profile, to see which ones are signed in. It also reads the profiles' names, to tell them apart. It reads all of it read-only and into memory, takes only the YouTube cookies and lets them go after the request. It never writes them anywhere and never asks Google who the user is. Only the requests for the user's account are signed in: searches, pages, similar songs and the audio stay anonymous.

Apple Music works the same way with one cookie, `media-user-token` of `music.apple.com` (not containers, private windows or partitioned storage), from the profile the user chose. It goes to two places, each keeping it in memory only: the windowless view of music.apple.com that reads the library (closed after ten minutes without a request or on sign-out), and, when an Apple song plays, the playback helper, as the first line on its standard input (never an argument or an environment variable, so no `ps` or `/proc` shows it). Ocean Mist asks the library page for the library with `GET` requests only (its engine has no way to write), never for the user's name or email, and blocks every sign-out request before the page loads: when the block cannot be installed, the page is not opened. The helper blocks them too, asks the account for its subscription and its store and nothing else, and says codes and numbers, never a title, a name, an address or the sign-in. Nothing in the Apple account is changed. Apple's songs play as Apple's own audio, in Apple's own web player, inside the playback engine: Chromium with Google's licensed Widevine module (castlabs's build, which the user downloads on request behind a licence screen, its SHA-256 checked). Ocean Mist decrypts and unlocks nothing itself, and the helper checks for an active subscription each time it starts. Chromium's sandbox always stays on: where the system forbids it and the package's profile does not cover the engine, the page shows a one-time administrator step (`engine/allow-sandbox.sh`, a profile for that one file) that the system runs after its own password window (`pkexec`: Ocean Mist never sees the password), or, where there is no such window, a command for the user's terminal. No Apple developer token, key or certificate is used or committed: the page's own player makes the requests, and Ocean Mist never reads the token that page holds.

## Tracking and delivery

Every change (code, bug fixes, enhancements, docs, research and repository operations) belongs to an issue with a milestone in `NahuelGenchi/ocean-mist`, reused or created before editing. Every new feature, and every other work item, gets its own new branch created from the latest `origin/main` for that issue: `<type>/<issue>-<slug>` (`feat`, `fix`, `enh`, `docs`, `research`, `ops`). Never reuse a branch for a second feature, never mix two issues on one branch, and never push to `main`. Use `type: summary (#N)` commits. Delete the branch after its PR merges. PRs follow `.github/pull_request_template.md`: a standalone `Closes #N` line, the issue's milestone, and `Refs #N` for unfinished parent work. Decisions, exact changed paths and blockers go in the issue or PR. See `CONTRIBUTING.md` and `docs/TRACKING.md`.

## Final report

Report the issue, the PR and what changed. Keep these separate: source checks (exact commands and outcomes, or "none run"), live player checks (the same), and source/diff review scope.
