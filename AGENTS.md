# Agent instructions

## The project

Ocean Mist is a music player for Linux with the look of Windows Media Player 9: the sculpted frame, the visualizations, a 10-band equalizer, a media library, internet radio, playlists, YouTube Music, and your Apple Music and Spotify libraries, whose songs play through a playback engine the user downloads on request. The interface is a local web page (`ui/`) shown in a frameless WebKitGTK window; `player.py` owns the window and a small HTTP server bound to 127.0.0.1 that feeds the page. There is no build step and nothing to install beyond GTK 3, WebKitGTK 4.1 and GStreamer; the Python side uses the standard library only. `README.md` describes the features.

It is an unofficial fan project, not affiliated with Microsoft, and licensed under GPL-3.0-or-later (`LICENSE`).

Never describe something as working or complete unless a recorded check establishes it. A syntax check is not proof that the player behaves.

## Commands

- `python3 player.py [FILES OR FOLDERS...]` runs the player.
- `python3 player.py --serve PORT [FILES...]` serves the interface without a window, for work on the page alone, at the address it prints (`http://127.0.0.1:PORT/TOKEN/`, with a new random token each time, as in the window). The server answers only requests whose Host is `127.0.0.1:PORT`, and the page runs under a Content-Security-Policy (`PAGE_POLICY` in `player.py`): no inline script or event attribute, nothing loaded or asked from another address.
- `python3 -m py_compile player.py library.py tags.py radio.py mpris.py ytmusic.py firefox.py apple.py spotify.py engine.py`, `for f in ui/*.js engine/helper/*.js; do node --check "$f"; done` and `bash -n engine/allow-sandbox.sh` are the source checks. There is no test suite yet.
- `packaging/build-deb.sh [FOLDER]` builds `FOLDER/ocean-mist_VERSION_all.deb` (default `dist/`, which git ignores) from the last commit (a rebuild of the same commit gives the same bytes on the same tools); `OCEAN_MIST_VERSION=0.3.0` makes a release build (releases so far: 0.1.0, 0.1.1, 0.2.0, 0.3.0). It needs git and dpkg-deb, installs nothing and needs no root. `dpkg-deb --info FILE` and `dpkg-deb --contents FILE` show what it made.
- `OCEAN_MIST_DEBUG=1` logs the HTTP requests and enables the web inspector.
- `python3 ytmusic.py search|album|artist|playlist|radio|audio ...` prints what the YouTube Music engine gets, without the player (the full list is in its docstring).
- `python3 firefox.py` says which Firefox profiles have a YouTube, an Apple Music and a Spotify sign-in, without printing any cookie.
- `python3 engine.py` says whether the playback engine is installed and whether this system restricts user namespaces (read-only); `python3 engine.py check` starts the installed engine for a moment and checks that its sandbox works.
- `python3 apple.py` opens Apple's page with the Apple Music sign-in of the most recently used Firefox profile that has one, and prints counts of what the library holds: no titles, no account details. It reads the owner's account, read-only.
- `python3 spotify.py [FIREFOX PROFILE]` opens Spotify's page the same way (the profile with a sign-in unless one is named) and prints, for each kind of the library, how many of how many came in: no titles, no account details. It reads the owner's account, read-only.

## Working well here

- Start from the active issue, then read only the code involved.
- The look is the point. The frame is measured against the original player, so compare with a reference before changing its shape, sizes or colors, and say in the PR what was compared.
- Keep it dependency-free: no build step, no Python packages, no JavaScript libraries, unless the issue says otherwise.
- Anything bundled from elsewhere (fonts, images, sounds) needs a license compatible with GPL-3.0-or-later, its notices next to the files and a line in the README credits, as in `ui/fonts/`.
- Never run a check against the owner's own player or settings. Use a separate instance and scratch folders, and keep it muted:

  ```sh
  T=/tmp/ocean-mist-test/Issue123
  OCEAN_MIST_APP_ID=io.github.nahuelgenchi.OceanMistTest.Issue123 \
  XDG_CONFIG_HOME=$T/config XDG_CACHE_HOME=$T/cache XDG_DATA_HOME=$T/data python3 player.py
  ```

  Settings live in `$XDG_CONFIG_HOME/ocean-mist/state.json`. Write it before the first launch, as `{"settings": {"muted": true, "folders": ["/tmp/ocean-mist-test/Issue123/music"]}}`: muted, and with the check's generated sample music as the media library, which otherwise scans `~/Music`.
- Other checks may be running at the same time, so each instance gets an app id and scratch folders of its own, named after its check (`Issue123` above, `Issue123B` for a second instance). The app id is the instance's name on the session bus. Its media controls (MPRIS) answer at the app id with `org.mpris.MediaPlayer2` in place of `io.github.nahuelgenchi`, here `org.mpris.MediaPlayer2.OceanMistTest.Issue123`; send the check's media-control calls there and nowhere else. A launch under an app id that is already on the bus goes to the instance holding it: the files open there, replacing its My Music, and the new process exits at once, without a word. So before a windowed launch, list the Ocean Mist names on the bus and make sure neither of the instance's names is there:

  ```sh
  gdbus call --session --dest org.freedesktop.DBus --object-path /org/freedesktop/DBus \
    --method org.freedesktop.DBus.ListNames | grep -o "'[^']*OceanMist[^']*'"
  ```
- WebKitGTK behavior worth knowing: script run from the host counts as a user gesture, so it hides autoplay problems; a seek on a song that has never played is ignored; a cross-origin stream is silent through Web Audio, which is why radio goes through the local relay; media only loads in a real, visible window. It cannot play HLS, which is why YouTube Music songs reach the page as MP4 fragments through Media Source; there, a seek made before the song first plays does work. An ephemeral view (`is_ephemeral`) still sets up the default context's cache and data folders on disk; only an ephemeral `WebContext`, which the player uses, keeps everything in memory.
- A check that signs in uses the owner's own Firefox sign-in, so it stays read-only and reports counts, never titles. Likes and playlist changes are checked against a local stand-in for YouTube Music; they are tried on the owner's account only with the owner's go-ahead.
- Apple Music's library is checked against a stand-in page on `music.apple.localhost` (a MusicKit-like object over invented songs) for everything that has a shape: paging, sign-in states, errors, the block on sign-out requests. The owner's own sign-in is used for one read-only run that reports counts and statuses. WebKit gotchas there: Apple's page crashed the web process a few seconds after it loaded in a view with media, Media Source, encrypted media, WebGL, Web Audio, images or hardware acceleration on, so the windowless view switches them all off (it is only a source of data); and WebKit does not send a `SameSite=None` cookie that is not `Secure`, so a stand-in's token must be `Lax`.
- Spotify's library is checked the same way against a stand-in page on `spotify.localhost` (an invented sign-in and the page's own requests over invented songs; `window.__omProduct` says the account's plan, which the playback helper takes only from a stand-in, and `__omOps` its answers), for everything that has a shape: paging, sign-in states, errors, the block on sign-out requests, and the plan gate. The owner's own sign-in is used for one read-only run that reports counts and statuses. Things Spotify's real page does that a stand-in has to copy: the library's `libraryV3` takes a `filters` variable (`Playlists`, `Albums`, `Artists`) that the page's own first request does not send, and the playlists' count includes Liked Songs; an album's songs come under `tracksV2` and name no album; after a few documents in one windowless view the page shows a notice (`data-testid="error-page"`) that this browser cannot play, in place of its player, and a new view opens it again; and in the engine, the page empties the song's media element once, at 0 s, right after it starts.
- The playback engine is checked in layers, each against a stand-in for the layer below it. The player and `engine.py` run against a stand-in runtime (a script that speaks the helper's protocol, put where the runtime goes and "downloaded" from a local zip, so the 117 MB download is never repeated; the downloader is checked the same way, with the pinned address, size and checksum handed to an injected fetch). The helper (`engine/helper/main.js`) runs in the real castlabs runtime, started by the real `engine.py`, against a stand-in page on a `.localhost` name with an invented sign-in, for each service (`--site=` accepts only such a name; anything else stays Apple's or Spotify's own site). A last, muted and read-only run of the whole player on Apple's own site uses the owner's Firefox sign-in and reports statuses and counts, never a title; do it only with the owner's go-ahead, because a song streaming there can stop one playing on the owner's other devices. Spotify's own site is checked the same way, with the same go-ahead: Spotify plays one stream per account, so a song played there stops one on the owner's other devices.
- Ubuntu 24.04 and later let a program create the user namespaces Chromium's sandbox needs only if an AppArmor profile names it. A check started from a program that has a profile of its own (a sandboxed terminal or editor, say) inherits that profile, which may allow them, so it can pass where a launch from the menu would not. The menu's way is `systemd-run --user --collect -- <program>`; without the profile it ends with Chromium's "SUID sandbox helper" message, which `engine.py` turns into the page's one-time step. Never switch the sandbox off (`--no-sandbox`) to make a check pass.
- The package's maintainer scripts run as root on other people's machines, so keep them to loading and unloading the one profile (and leaving it unloaded when the administrator switched it off with `aa-disable`) and byte-compiling the player's own files, make a failure of either never fail the install, and keep them out of every home folder. Their checks run the scripts with stand-ins for `apparmor_parser`, `aa-status`, `py3compile` and `py3clean`, and install, upgrade, remove and purge the package with the real `dpkg` into a scratch root (`dpkg --root=DIR --force-not-root --force-script-chrootless`, not as root), then once more with the real `dpkg`, scripts, `py3compile` and `py3clean` in a private user and mount namespace as an unprivileged user (`unshare --user --map-root-user --mount --pid`, with `/usr` and `/etc` as overlays that write to a scratch folder; the folders the package shares with the system are first made in that writable layer, because the real root's own folders are not writable from there). Never install the package on the machine a check runs on, and never load a profile: that is the owner's step, with one script of their own. Both of the engine's profiles (the package's, and the one `engine/allow-sandbox.sh --print` writes) must parse on AppArmor 4.0, the oldest the package allows (Ubuntu 24.04 has 4.0.1): 5.0 declares variables of its own, such as `@{exec_path}`, which 4.0 refuses as never declared (#38), so the builder refuses any variable but `@{HOME}`. The builder parses both with `apparmor_parser -Q -T -K`, which parses and loads nothing (it skips that, with a note, where the system's AppArmor is older than 4.0). Before a release, also parse them with Ubuntu 24.04's parser: download its `apparmor` package (ask the owner first), check its SHA-256 against packages.ubuntu.com, unpack it with `dpkg-deb -x FILE DIR` into a scratch folder (never install it), and build with `OCEAN_MIST_APPARMOR_ROOT=DIR`. The package also needs AppArmor 4.0 or later when AppArmor is installed (`Breaks: apparmor (<< 4.0~)`), because the profile starts with `abi <abi/4.0>`.
- The administrator step changes the system, so a check never runs it: the host and page checks put a stand-in where `pkexec` goes (`engine.PKEXEC`) and look at what it was asked. The real password window is tried by the owner, in a separate test instance with its own scratch folders.
- Memory is measured in a test instance as the PSS of every process the player started (`Pss` of `/proc/PID/smaps_rollup`, summed over its process tree, which shares out what processes have in common), sampled every two seconds while a state lasts, before and after a change in the same session; Apple's and Spotify's pages vary by some 30 MB from run to run. README's "How much memory it uses" has the numbers. Tried and kept out, because each changed how the player looks, sounds or behaves: WebKit's hardware acceleration off (30 MB less, but the page then runs its frames on a 64 Hz timer in a 60 Hz window, and a full-screen visualization takes four times the processor), and switching it on only in full screen (WebKit keeps the memory once it was on); WebKit's frames in shared memory (`WEBKIT_DMABUF_RENDERER_FORCE_SHM`: 10 MB less, a tenth of a core more in full screen); GStreamer's `faad` before FFmpeg's AAC decoder (20 MB less, but it decodes to 16 bits and so clips the peaks a loud song has over full scale, before the volume and the equalizer could lower them); WebKit's `ServiceWorkers` feature off in a library view (Spotify's page then fails, and WebKit starts its network process over and over). In the engine (#56): no stylesheets (7 MB less on Apple's page, but Spotify's page loads parts of its player with theirs and then plays nothing); Chromium's off-screen drawing with painting stopped (more memory and twice the processor); V8's lite mode (a few MB); a light first page for Spotify (its "not found" page has no player, and search saves nothing over the home page); the network service in the main process (the build has no such switch any more); the GPU process in the main process (it is sandboxed, so no); listening inside the service's page instead of a second one (the page would hear its own output). For the libraries (#58): Spotify's library in the engine, in a second window there (some 400 MB more, more than the view it would replace) or in the engine's own page (hidden, it never makes the `libraryV3` request the lists are read with, and laid out but invisible it still does not, for some 60 MB more); letting go of a library view's WebContext to end its network process (WebKitGTK crashes as the WebContext is finalized, at once or seconds after its view is gone). The engine's processes are counted with `SwapPss` too: when the system is short of memory, swapped-out pages drop out of `Pss` and make a run look smaller than it is.
- Record what a check covered and what it did not, in the PR.

## Private data

Music files, personal playlists, `state.json`, the tag and cover cache, and any account credentials, cookies or tokens stay out of commits, issues and PRs, and out of a check's output. So do YouTube's audio addresses (`googlevideo.com`): they carry the IP address of whoever asked for them, so never print them in a check's output either. No client id, secret or key for a service is ever committed. Screenshots use generated sample music with invented names, never a real library.

Nothing from a streaming service is written to disk: the streaming services' lists, searches, covers and the signed-in libraries stay in memory, the covers for the media controls go to `$XDG_RUNTIME_DIR` and are removed on close, the web contexts (the page's, and the windowless ones that read Apple Music and Spotify) are ephemeral, and `state.json` holds files and stations only, plus the Firefox profile the user chose to sign in with, for each service. The one other thing in `$XDG_RUNTIME_DIR` is the folder of rules that keep the services' pages from signing the user out; it holds no data from a service and goes on close. The playback engine's folder (`$XDG_DATA_HOME/ocean-mist/engine`) holds the runtime that was downloaded and the files Chromium and Google's Widevine module keep there, and nothing of a service's: the page's session lives in memory. A playlist the user saves is the one exception, on purpose: a service song in it is saved as its web address and `Artist - Title`, nothing else. Keep it that way: storing anything else from a service is the owner's decision.

The sign-in stays Firefox's. Ocean Mist reads Firefox's cookie files only while the user is signed in or signing in: signed in, only that of the profile the user chose; signing in, those of every profile, to see which ones are signed in. It also reads the profiles' names, to tell them apart. It reads all of it read-only and into memory, takes only the YouTube cookies and lets them go after the request. It never writes them anywhere and never asks Google who the user is. Only the requests for the user's account are signed in: searches, pages, similar songs and the audio stay anonymous.

Apple Music works the same way with one cookie, `media-user-token` of `music.apple.com` (not containers, private windows or partitioned storage), from the profile the user chose. It goes to two places, each keeping it in memory only: the windowless view of music.apple.com that reads the library (closed after ten minutes without a request or on sign-out), and, when an Apple song plays, the playback helper, as the first line on its standard input (never an argument or an environment variable, so no `ps` or `/proc` shows it). Ocean Mist asks the library page for the library with `GET` requests only (its engine has no way to write), never for the user's name or email, and blocks every sign-out request before the page loads: when the block cannot be installed, the page is not opened. The helper blocks them too, asks the account for its subscription and its store and nothing else (`engine.py` keeps the store's two letters in memory, so the next start opens the page there), and says codes and numbers, never a title, a name, an address or the sign-in. Nothing in the Apple account is changed. Apple's songs play as Apple's own audio, in Apple's own web player, inside the playback engine: Chromium with Google's licensed Widevine module (castlabs's build, which the user downloads on request behind a licence screen, its SHA-256 checked). Ocean Mist decrypts and unlocks nothing itself, and the helper checks for an active subscription each time it starts. Chromium's sandbox always stays on: where the system forbids it and the package's profile does not cover the engine, the page shows a one-time administrator step (`engine/allow-sandbox.sh`, a profile for that one file) that the system runs after its own password window (`pkexec`: Ocean Mist never sees the password), or, where there is no such window, a command for the user's terminal. No Apple developer token, key or certificate is used or committed: the page's own player makes the requests, and Ocean Mist never reads the token that page holds.

Spotify works the same way with the cookies its web player signs in with, `sp_dc` and the companions (`sp_key`, `sp_t`; not containers, private windows or partitioned storage), from the profile the user chose. They go to two places, each keeping them in memory only: the windowless view of open.spotify.com that reads the library (closed after ten minutes without a request or on sign-out), whose hook keeps the page's own requests in memory so a page of the library can be asked again with a different offset, and, when a Spotify song plays, the playback helper, on its standard input (never an argument or an environment variable, so no `ps` or `/proc` shows them). Ocean Mist asks the library page for the library with read-only requests, never for the user's name or email, and blocks every sign-out request before the page loads: when the block cannot be installed, the page is not opened. The helper blocks them too, reads the account's plan from the page's own answer when it starts and plays only for a plan it knows to be Premium (a plan it cannot read in time stops it too), and says codes and numbers, never a title, a name, an address or the sign-in. Nothing in the Spotify account is changed. Spotify's songs play as Spotify's own audio, in Spotify's own web player, inside the same playback engine as Apple Music's. No Spotify client id, secret or key is used or committed, and there is no call to Spotify's Web API: the page's own player makes the requests. The access token the page holds stays in that page: the hook asks the page's own requests again from inside it, with the page's own headers, and only the answers reach Python; the helper sends no token of its own.

## Tracking and delivery

Every change (code, bug fixes, enhancements, docs, research and repository operations) belongs to an issue with a milestone in `NahuelGenchi/ocean-mist`, reused or created before editing. Every new feature, and every other work item, gets its own new branch created from the latest `origin/main` for that issue: `<type>/<issue>-<slug>` (`feat`, `fix`, `enh`, `docs`, `research`, `ops`). Never reuse a branch for a second feature, never mix two issues on one branch, and never push to `main`. Use `type: summary (#N)` commits. Delete the branch after its PR merges. PRs follow `.github/pull_request_template.md`: a standalone `Closes #N` line, the issue's milestone, and `Refs #N` for unfinished parent work. Decisions, exact changed paths and blockers go in the issue or PR. See `CONTRIBUTING.md` and `docs/TRACKING.md`.
